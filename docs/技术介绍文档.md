## 一、背景与定位

RT-Thread 自 2006 年创立以来，已发展成为国内最具影响力的开源实时操作系统。凭借 20 年的生态积累，其在工业控制、汽车电子、消费产品等领域已部署超过 25 亿台设备，拥有 25+ 万开发者。

RT-Thread 的核心优势在于其**统一的设备框架**和**完整的中间件生态**。特别是在网络领域，RT-Thread 提供了标准化的 WLAN 框架（`wlan_dev`/`wlan_prot`/`netdev`）和 SDMMC/SDIO 总线抽象层（`mmcsd_core`），为 WiFi 驱动的高效移植奠定了基础。

**Aerolynq® WiFi-BT-Host-Driver** 正是基于这一理念，将 Infineon AIROC™ WHD（Wi-Fi Host Driver）与 BTStack 蓝牙协议栈深度适配到 RT-Thread 生态，通过标准 SDIO 总线框架驱动 Aerolynq® 的 CYWL 系列 WiFi/BT 组合模块，实现以下关键优势：

1. **原生 SDIO 总线支持** — 基于 RT-Thread 标准 `mmcsd_core` 框架，无需额外总线驱动
2. **Host 架构设计** — 协议栈运行在主 MCU，SDIO 高速通信，低延时高吞吐
3. **全面的芯片覆盖** — WiFi 4/5/6 + 蓝牙 5.x/6.0 一体化支持（已适配 CYWL6208 / 6209 / 6302 / 6305 / 6612，CYWL6632 预告中）
4. **跨平台可移植性** — 驱动已接入 RT-Thread SDMMC 架构，换 MCU 平台只需调通该平台的 `drv_sdmmc.c`（SDIO 数据通信正常），WiFi 驱动即可直接运行；已在本仓库 STM32H743/art pi2等多个平台上完整验证

> **读图要点**
>
> - **WiFi 与蓝牙是两条独立链路**：WiFi 走 SDIO → `mmcsd` → `drv_sdmmc`；蓝牙走 UART → `rt_serial` → `drv_usart`。
>   两者除了「RTOS 抽象层」和「HAL 适配层」外没有共享，BTStack **不经过** WHD 或 SDIO。
> - **RTOS 抽象层位于 WHD / BTStack 之下、HAL 之上**：为上层提供线程与同步原语；
>   HAL 适配层本身直接调用 `rt_thread_*` / `rt_pin_*` / `rt_serial`，不依赖该抽象层。
> - **卡中断三级兜底是 Aerolynq 移植层的能力**，不是 RT-Thread 框架自带特性。
>   断路优先使用 OOB `HOST_WAKE` GPIO；其次带内 `SDIOIT`（依赖 BSP 的 `drv_sdmmc.c`
>   转发 `mmcsd_signal_sdio_irq()`）；两者都不可用时启动 2ms 轮询线程兜底。

### 2.2 核心设计决策：为什么选择 RT-Thread mmcsd 框架？

**问题背景**

传统 WiFi 驱动方案为每个 MCU 平台实现一套独立的 SDIO 总线驱动。这导致：

- ❌ 代码重复：STM32 版、GD32 版、先楫版等，总线逻辑复写
- ❌ 适配周期：新 MCU 适配需要 3-6 个月独立开发
- ❌ 稳定性差：各平台代码质量参差不齐，难以维护

**解决方案：复用 RT-Thread 标准框架**

Aerolynq® 方案将 SDIO 驱动委托给 RT-Thread 的标准 `mmcsd_core` 框架：

```
WiFi 驱动代码（whd_bus_sdio_protocol.c，Infineon 上游）
    ↓
cyhal_rtthread.c（Aerolynq 移植层）
    ├─ cyhal_sdio_send_cmd()      → mmcsd_send_cmd(host, &cmd, 0)      [CMD52]
    └─ cyhal_sdio_bulk_transfer() → mmcsd_send_request(host, &req)     [CMD53]
    ↓
mmcsd_core.c（RT-Thread MMC 核心：host 抽象、卡枚举、总线宽度/时钟协商）
    ↓
drv_sdmmc.c（具体平台 SDMMC 驱动——由各 BSP 提供）
    ↓
硬件（SDMMC 控制器）
```

其中卡枚举与 VID/PID 匹配发生在 RT-Thread SDIO 框架（`dev_sdio.c`）：
`mmcsd_detect` 线程完成枚举后，由 `dev_sdio.c` 匹配本驱动注册的
`rt_sdio_driver` 并回调 `probe`。

配套使用的 RT-Thread SDIO 框架 API（`dev_sdio.c`）：
`sdio_register_driver()`（注册驱动）、`sdio_attach_irq()`（带内 SDIOIT 中断）、
`sdio_set_block_size()`（块长协商）、`sdio_detach_irq()`。

**实现细节**

WiFi-BT-Host-Driver 中的 `cyhal_rtthread.c` 仅需做两件事：

**1️⃣ 注册一个标准 `rt_sdio_driver`**

```c
// Porting/rt-thread/common/cyhal_rtthread.c
static struct rt_sdio_driver _sdio_drv = {
    .name   = CYHAL_SDIO_DRIVER_NAME,
    .probe  = _sdio_probe_callback,
    .remove = _sdio_remove_callback,
    .id     = &_sdio_dev_id,
};

// 驱动初始化时注册
sdio_register_driver(&_sdio_drv);  // 注册完成，SDIO 总线会自动检测 WiFi 芯片
```

RT-Thread 的 `mmcsd_detect` 线程会自动扫描 SDIO 总线，匹配 WiFi 芯片的 VID/PID，然后调用 `probe` 函数。

**2️⃣ 所有 SDIO 命令通过 mmcsd 转发**

```c
// CMD52（寄存器读写）—— cyhal_sdio_send_cmd()
mmcsd_host_lock(host);
rc = mmcsd_send_cmd(host, &cmd, 0);
mmcsd_host_unlock(host);

// CMD53（块数据读写）—— cyhal_sdio_bulk_transfer()
mmcsd_host_lock(host);
mmcsd_send_request(host, &req);
mmcsd_host_unlock(host);
```

> **复用边界（诚实说明）**
>
> 复用的是 `mmcsd_core` 提供的 **host 抽象、SDIO 卡自动枚举、总线宽度与时钟协商**（`mmcsd_set_clock`），
> 命令收发由移植层自行拼装 `rt_mmcsd_cmd` / `rt_mmcsd_req` 完成，
> **未**走 `dev_sdio.c` 封装的 `rt_sdio_*` 公共 API（`sdio_io_rw_direct` / `sdio_io_rw_extended`）。
>
> 这一点在实践中很重要：`dev_sdio.c` 的字节模式分支对块长做了额外处理
> （`blocks == 1 && blksize <= 512` 时按块长编码，否则走块模式），
> 自行拼装命令时必须自行保证块长与模式语义一致 —— 本方案早期版本正是在这里踩过
> 「CMD53 字节模式长度非 2 的幂时超时」的坑。

**收益对比**

| 指标                   | 传统方案（自建 SDIO 驱动）     | Aerolynq® 方案（复用 mmcsd）               |
| ---------------------- | ------------------------------ | ------------------------------------------- |
| **新 MCU 适配**  | 3-6 个月（需独立写 SDIO 驱动） | **1-2 周**（Kconfig 开关 + 已有 BSP） |
| **SDIO 代码量**  | 每平台 2000+ 行                | **约 200 行**（仅命令转发与中断路由）    |
| **稳定性**       | 平台间代码质量差异大           | 枚举/协商集中在经历大量验证的 `mmcsd_core` |
| **维护成本**     | N×平台 = N 倍维护工作         | 仅 1 个中间层                               |
| **跨平台一致性** | 低（各平台 bug 不同）          | 高（标准框架行为一致）                      |

> **关键优势**：本驱动以标准 `rt_sdio_driver` 注册到 RT-Thread SDIO 框架，
> SDIO 总线的枚举、VID/PID 匹配、总线宽度与时钟协商、命令收发全部由框架与目标平台的
> `drv_sdmmc.c` 承担。因此换 MCU 平台时，实际工作收敛为**调通该平台的 `drv_sdmmc.c`**
> （确认 CMD52 寄存器读写与 CMD53 块传输正常），WiFi 驱动即可直接运行，协议栈代码无需改动。
>
> 需要注意的是，这**不等于**「零代码」：中断路由（OOB / 带内 / 轮询三级兜底）
> 与 `rt_mmcsd_cmd` / `rt_mmcsd_req` 的拼装仍需在移植层完成，
> 且不同 MCU 的 SDMMC 驱动成熟度不同，这部分工作量无法完全免除。
> （D-Cache 一致性由 WHD 上游的 `whd_bus_sdio_protocol.c` 处理，一般无需额外干预。）

## 三、性能对比：AT 指令方案 vs 原生 SDIO 方案

### 3.1 架构对比

**❌ 传统 AT 指令方案（模组内部运行协议栈）**

```
主 MCU                          WiFi 模组
┌─────────────────┐            ┌──────────────────────┐
│ 应用层          │            │ 模组 MCU             │
│ (纯业务逻辑)    │            │ └─ lwIP 协议栈        │
│ (无协议栈)      │ ←AT指令→    │ └─ WiFi MAC/PHY      │
└─────────────────┘(UART)      └──────────────────────┘

瓶颈：
• UART 波特率通常 115200 bps（8N1 下有效载荷约 11.5 KB/s ≈ 92 kbps）
• AT 指令解析开销 + 模组内协议栈负担
• 每次交互存在指令往返延时
```

> 注：AT 方案的瓶颈是**协议开销与单次往返延时**，而非链路层带宽上限。
> 即便把 UART 提到 3 Mbps，单条 AT 指令的请求-应答往返仍是毫秒级，
> 且模组内 lwIP 协议栈会吃掉相当一部分有效吞吐。

**✅ Aerolynq® Host 架构方案（协议栈在主 MCU）**

```
主 MCU                          WiFi 芯片
┌──────────────────┐           ┌────────────────┐
│ 应用层           │           │ WiFi MAC/PHY   │
│ lwIP 协议栈      │ ←SDIO→    │ (固件)         │
│ WHD 驱动         │ 4-bit     │                │
│                  │ 50MHz     │                │
└──────────────────┘           └────────────────┘

核心优势：
• **协议栈在主 MCU** → 应用直接访问 TCP/IP，跳过 AT 指令解析
• **SDIO 高速总线** → 4-bit @ 50MHz = 200 Mbps 理论带宽
• **完整驱动控制** → 可调试、可优化、支持高级功能（漫游/WPA3/低功耗）
• **实测吞吐** → CYWL6302 上 5GHz 约 48-51 Mbps、2.4GHz 约 40-50 Mbps（iperf，详见 §3.2）
```

> 但仓库内**没有**对应的已验证 BSP 或测试记录，因此一律标注为「可移植待验证」，不写「已覆盖」。
>
> 仓库 `Porting/platform_mcu/gd32f470/` 目录下只有一个 `cybt_platform_diag_gd32f4xx.c`，
> 是可选的蓝牙 HCI UART 诊断辅助文件（纯软件日志打印），**不代表** GD32F470 上的 WiFi 部分已验证。

**适配工作量**

- **已有 RT-Thread BSP 且支持 SDMMC**：仅需在 Kconfig 中启用驱动并配置引脚 → **数天**（无总线代码）
- **RT-Thread BSP 存在但需 SDMMC 驱动**：需编写 `drv_sdmmc.c` → **1-2 周**
- **无 RT-Thread BSP**：需完整 BSP 开发 → **2-4 周**

**MCU 最低要求**

- ARM Cortex-M3/M4/M4F/M7/M33/M55 或 RISC-V
- ≥ 512 KB Flash（推荐 ≥ 2 MB）
- ≥ 128 KB SRAM（推荐 ≥ 1 MB）
- 支持 SDIO 接口（本包当前仅提供 SDIO 总线适配，SPI 适配尚未提供）

```bash
# 进入 RT-Thread 项目目录
cd your-rt-thread-project

# 打开配置菜单
scons --menuconfig
```

**RT-Thread Components → WiFi → WiFi-BT Host Driver (WHD)**

**WiFi 配置示例**

```
[*] Using WiFi-BT-Host-Driver (Aerolynq CYWL modules)
    (latest) version
    Select WiFi Generation (WiFi 5 (802.11ac))
        ├─ WiFi 4 (802.11n)
        ├─ WiFi 5 (802.11ac)
        └─ WiFi 6 (802.11ax)
    Select WiFi5 Module (CYWL6302)
        ├─ CYWL6208
        ├─ CYWL6209
        ├─ CYWL6302
        ├─ CYWL6305
        └─ CYWL6612
    (PC.4)  WiFi REG_ON pin name           # 电源使能脚（GPIO）
    (PC.5)  HOST_WAKE_IRQ pin name         # 卡中断脚（留空则用带内 SDIOIT）
    [ ]     Using resources in external storage (FAL)
        (whd_combined) Partition name for combined firmware
        (1024)         Block size for resources
    [ ]     Enable Other WIFI Features
        (8)    WHD thread priority
        (5120) WHD thread stack size
        [ ]     Enable WPA3-SAE Support
        [ ]       Enable WPA3 supplicant debug log
        [ ]       Enable WPA3 hex dump log
        [ ]     Enable Low-Power Offload Commands
        [ ]     Enable WiFi Roaming APIs
        [ ]     Enable WiFi MFG RF Test
```

> **HOST_WAKE_IRQ 留空会怎样？**
> 留空则不使用 OOB（Out-Of-Band）GPIO 中断，改为由 WHD 线程轮询带内 `SDIOIT`。
> 两者都不可用时，移植层会启动 2ms 轮询线程兜底（见 §2.1）。
>
> **WPA3 的前置条件**
> `Enable WPA3-SAE Support` 会自动选中 `PKG_USING_MBEDTLS`（需 ECP / HKDF / HMAC_DRBG / bignum），
> 并编译 `External/wpa3-external-supplicant/`。额外开销约 40KB Flash / 10KB RAM。
> 固件需上报 `WHD_FWCAP_SAE_EXT` 能力，否则编译通过也无法建立 WPA3-SAE 连接。

**蓝牙配置示例（可选）**

```
[*] Enable Bluetooth (HCI UART)
    (uart4)   Bluetooth HCI UART device name
    (PB.9)    BT UART TX pin name
    (PB.8)    BT UART RX pin name
    (PB.14)   BT UART RTS pin name (hardware flow control)
    (PB.15)   BT UART CTS pin name
    (115200)  Baud rate for firmware download
    (3000000) Baud rate for normal operation
    ()        BT REG_ON pin name
    ()        BT DEV_WAKE pin name
    ()        BT HOST_WAKE pin name
    [ ]       Enable Bluetooth sleep mode
    [ ]       Enable HCI data trace (TX/RX packets)
    [*]       Enable BTStack Library
        Bluetooth Mode (BLE Only)
            ├─ BLE Only (Low Energy)
            └─ Dual Mode (Classic + BLE)
        CPU Core (Cortex-M4/M4F)
```

> **BTStack 不是本包自带的**
> BTStack 协议栈由 Infineon 单独分发（BTStack EULA，见其 `LICENSE.txt`），
> 需从 <https://github.com/Infineon/btstack> 下载后解压到 `External/btstack/`。
> 该目录不存在时，构建阶段会自动跳过 BT 源码，`Enable Bluetooth` 静默失效。
>
> **UART 必须支持硬件流控（RTS/CTS）**，否则 HCI 固件下载阶段会因缓冲区溢出而失败。
> 固件下载波特率支持 115200 / 921600 / 1000000 / 2000000 / 3000000，
> CYW43xx 在 3 Mbps 下完成固件下载，正常工作阶段同样推荐 3 Mbps。
>
> **睡眠模式**需要同时配置 DEV_WAKE 与 HOST_WAKE 引脚，CYW43xx 的唤醒极性固定为低有效。

### 5.2 基本使用

**WiFi 连接（WLAN API）**

```c
#include <wlan_mgnt.h>

// 扫描可用网络
rt_wlan_scan();

// 连接到 WiFi 网络
rt_wlan_connect("MySSID", "password");

// 检查连接状态
if (rt_wlan_is_connected()) {
    rt_kprintf("WiFi connected!\n");
}

// 获取 IP 地址
rt_wlan_get_info(&info);
rt_kprintf("IP: %s\n", info.ip.addr_list[0].address);
```

**常用 MSH 命令**

> `wifi` 是 RT-Thread 原生 WLAN 命令（来自 `components/drivers/wlan/dev_wlan_cmd.c`），
> 因为 WiFi 设备注册为标准 `wlan_dev`，这些子命令天然可用。
> 下列 `wifi_roam` / `wifi_ps` / `wifi_arp` / `wifi_wowl` / `ble_*` 是本驱动包通过
> `MSH_CMD_EXPORT_ALIAS` 额外注册的命令。

```bash
# WiFi 扫描与连接（RT-Thread 原生 wifi 命令）
msh /> wifi scan                         # 扫描可用网络
msh /> wifi join SSID password           # 连接到 WiFi
msh /> wifi status                       # 查看连接状态
msh /> wifi ap SSID password             # 启动 AP 模式（热点）
msh /> wifi disc                         # 断开连接

# 网络诊断
msh /> ifconfig                           # 查看网络接口信息
msh /> ping 8.8.8.8                       # 测试网络连通性

# 低功耗（启用 [Enable Low-Power Offload Commands] 后）
msh /> wifi_ps                            # 查看当前省电模式与监听间隔
msh /> wifi_ps mode 2                     # 设置省电模式（0=off 1=PM1 2=PM2）
msh /> wifi_ps pm2_sleep 100              # PM2 唤醒后回睡延时（10~2000 ms，10 的倍数）
msh /> wifi_ps listen 10 dtim             # 设置监听间隔（DTIM 或 beacon 周期）
msh /> wifi_arp                           # 查看 ARP offload 状态
msh /> wifi_arp enable                    # 启用 ARP offload
msh /> wifi_wowl set magic net            # 启用 Wake on WLAN 能力标志

# 漫游（启用 [Enable WiFi Roaming APIs] 后）
msh /> wifi_roam                          # 查看全部漫游参数
msh /> wifi_roam trigger 2g -70           # 2G 漫游触发阈值（dBm）
msh /> wifi_roam period 10                # 漫游扫描周期（秒）

# 蓝牙（启用 BTStack 后）
msh /> ble gatt start                     # 初始化 GATT 服务
msh /> ble scan start                     # 启动 BLE 扫描
msh /> ble adv start                      # 启动广播
msh /> ble info                           # 查看蓝牙信息
```

### 5.3 高级功能

**WPA3 安全认证**

```bash
msh /> wifi join MySSID password          # 自动检测 WPA2/WPA3
```

**漫游（Roaming）**

启用 `Enable WiFi Roaming APIs` 后，WiFi 会自动在 AP 间无缝漫游。

**低功耗模式**

WiFi PM2 模式可将待机功耗降低至 < 200 µA（DTIM 10）。
相关命令（`wifi_ps` / `wifi_arp` / `wifi_tko` / `wifi_pf` / `wifi_wowl`）
需开启 `Enable Low-Power Offload Commands`。

**制造测试模式（MFG）**

启用 `Enable WiFi MFG RF Test` 后支持 WiFi 法规认证所需的制造模式，包括速率设置、功率调整等。
进入 / 退出命令为 `rf_mode` 与 `normalmode`，
PC 端可通过 `wl.exe --serial <COM口>` 下发命令。

## 附录：常见问题

**Q1：需要多少代码修改才能在新 MCU 上运行？**

A：如果目标 BSP 已提供可用的 `drv_sdmmc.c` SDMMC 驱动，**无需重写总线代码**。
仅需在 Kconfig 中启用驱动、配置引脚与中断源（OOB / 带内 / 轮询），
并确认 MPU 区域配置使 DMA 缓冲区可被 SDIO 控制器访问。

D-Cache 一致性已由 WHD 上游的 `whd_bus_sdio_protocol.c` 处理
（非对齐/不可 cache 缓冲区会走本地临时缓冲），一般无需额外干预。

**Q2：支持 SPI 接口吗？**

A：模组硬件层面支持 SPI，但**本驱动包当前只提供 SDIO 适配**（`cyhal_sdio`）。
SPI 适配（`whd_bus_spi_protocol.c` 上游已具备）尚未在 RT-Thread 移植层实现。

**Q3：可以离线升级固件吗？**

A：是的，支持 FAL 外部 Flash 存储和 MSH 命令行下载。
固件资源位于 `drivers/wifi-host-driver/resources/firmware/COMPONENT_CYWLxxxx/`，
外部 Flash 下载流程详见 `External/README.md`。

**Q4：低功耗模式下能定期唤醒吗？**

A：是的，支持 WiFi PM2 + DTIM 设置，可在 < 200 µA 待机功耗与快速响应间平衡。

**Q5：蓝牙和 WiFi 能同时工作吗？**

A：可以。CYWL 模块集成了 WiFi 和 BT 无线电。
但需要注意：**两条链路在硬件上是分开的** —— WiFi 走 SDIO，蓝牙走 UART（HCI），
需要占用独立引脚与独立 DMA/中断资源。
